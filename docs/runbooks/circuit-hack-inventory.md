# Circuit Hack inventory — keep / fork / scrub

Audit of the `Qbox_F913B4.base` recipe currently installed at
`~/dev/vzu/server-local/txData/Qbox_F913B4.base/`. The recipe was generated by
txAdmin on 2026-05-04 from upstream qbox and then extended for the prior
"Circuit Hack" Tebex product. This doc decides what survives the move into the
monorepo. Operating context lives in
[local-dev-server.md](local-dev-server.md).

## VZU resources

These three came from the prior Circuit Hack project and are the only material
that's actually *ours*.

### `vzu_circuit_hack` (v2.0.0)

- **Status:** **keep**, source-of-truth move into the monorepo.
- **What it is:** premium pipe-dream-style hacking minigame. Has a Tebex page
  (vzu.tebex.io) and a public GitHub at `vizuugit/vzu_circuit_hack`.
- **Author:** VZU Studio (`vizuu3d@gmail.com`).
- **Dependencies:** `ox_lib` (required), `oxmysql` (optional — falls back to
  in-memory persistence if absent).
- **Notable internal state:** `server/vzu_persistence.lua` ships in the
  resource but is intentionally *not* loaded by `fxmanifest.lua` due to a CFX
  loader skip; the rest of the code degrades gracefully to in-memory. This is
  documented inline in `fxmanifest.lua`. We inherit that note.
- **Action on monorepo migration:**
  1. Source moves to `resources/[vzu]/vzu_circuit_hack/` in the monorepo.
  2. `LICENSE.txt` ships with the resource (it's our own MIT — confirm before
     committing).
  3. Strip `vzu_circuit_hack-v2.0.0.zip` (release artifact, not source).
  4. Decide whether the GitHub repo stays separate or merges in. **Recommendation:**
     archive the standalone repo, treat the monorepo copy as canonical, keep
     a thin "see monorepo" README on the public repo for SEO/Tebex links. Defer
     to CMO + CTO; not blocking.

### `vzu_circuit_hack_test_zone` (v1.0.0)

- **Status:** **fork** into a dev-only path, **scrub from prod**.
- **What it is:** smoke-test rig that runs every Circuit Hack scenario from a
  single `/vzutest` command. Spawns characters, gives money, hands out
  vehicles, drives every difficulty level. Used during last-mile QA passes and
  for Tebex promo screenshots.
- **Risk if shipped:** anyone with the resource loaded gets free `$100,000`
  payouts and admin shortcuts. **Must not be ensured on a public-facing
  server.**
- **Action on monorepo migration:**
  1. Move source to `tools/dev-bench/vzu_circuit_hack_test_zone/`, *not*
     `resources/`.
  2. Make it loadable for local dev only — guarded by an explicit
     `ensure vzu_circuit_hack_test_zone` line in a `server.dev.cfg` fragment.
  3. The current `server.cfg` line (with the comment "remove esta linha
     quando terminar as capturas promo") gets removed in the cutover.

### `vzu_circuit_hack-v2.0.0.zip`

- **Status:** **scrub.**
- **What it is:** old release zip sitting next to the source folder. Unused at
  runtime, easy to grab the wrong one by mistake.
- **Action:** delete in the cutover. Canonical releases live on GitHub Releases
  for the `vzu_circuit_hack` repo (or the monorepo, once decided).

## Phone stack

`[npwd]` and `[npwd-apps]` add a phone UI to the game (like LSPDFR's phones).
Four resources:

- `npwd` — the core phone framework (NoPixel-style).
- `qbx_npwd` — qbox bridge.
- `npwd_qbx_garages` — garage app inside the phone.
- `npwd_qbx_mail` — mail app inside the phone.

`server.cfg` configures `set npwd:framework "qbx"` and leaves
`SCREENSHOT_BASIC_TOKEN` / `NPWD_AUDIO_TOKEN` empty (camera + voice messages
disabled until tokens are provisioned).

- **Recommendation:** **keep** for closed alpha. The phone is core to a modern
  RP server and the integration work is already done. Defer the camera/voice
  tokens to a follow-up.

## qbox base (`[qbx]`)

48 qbx resources are present, covering core, jobs, robberies, vehicles,
medical, police, properties, scoreboard, hud, and more. None of these are
modified locally — they are stock qbox. **Disposition: keep, vendor each with
its upstream commit pin** in the monorepo.

A handful of jobs we may not need on day-one alpha (`qbx_busjob`,
`qbx_garbagejob`, `qbx_taxijob`, `qbx_truckerjob`, `qbx_vineyard`,
`qbx_fireworks`, `qbx_lapraces`, `qbx_streetraces`, `qbx_recyclejob`,
`qbx_diving`, `qbx_divegear`, `qbx_weed`). These can stay loaded — the cost is
trivial and they give the world some life — but they're **prune candidates**
for a follow-up issue once the gameplay engineer has scoped the alpha mode.

**Disposition: keep all six.** Standard overlay; matches the [VEC-2 plan](/VEC/issues/VEC-2#document-plan)

## cfx-default (`[cfx-default]`)

Six folders: `[gamemodes]`, `[gameplay]`, `[local]`, `[managers]`, `[system]`,
`[test]`. These ship with FXServer and provide `mapmanager`, `chat`,
`spawnmanager`, `sessionmanager`, `hardcap`, `baseevents` — all `ensure`d in
`server.cfg`. **Keep as-is** when migrating; do not vendor (FXServer ships them).

## What we do *not* have today

Worth flagging because the [VEC-2 plan](/VEC/issues/VEC-2#document-plan) calls
for them:

- **`vector-anticheat`** — heuristic anti-cheat resource (this engineer's
  domain). Not present yet. To be created in a future issue under
  `resources/[vzu]/vector-anticheat/`.
- **Server-side migration runner.** Today, schema changes are applied by
  hand via Adminer. Acceptable for now — must be replaced before public alpha.
- **Centralised log shipper.** FXServer logs only land in
  `txData/default/logs/`. No Loki / no remote sink yet. Phase-1 deliverable.
- **Backup automation.** No nightly mysqldump cron, no S3 push. Phase-1
  deliverable.

## Sensitive material in the recipe

These need to be addressed *before* any cutover into the monorepo:

| File                                              | Issue                                                  | Action                                                            |
| ------------------------------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------- |
| `txData/Qbox_F913B4.base/server.cfg`              | Contains literal `sv_licenseKey "cfxk_…"`              | Replace with `sv_licenseKey "${LICENSE_KEY}"`, keep real value in `.env`. |
| `txData/Qbox_F913B4.base/server.cfg`              | `mysql_connection_string` has inline placeholder password | Switch to `${DB_USER}` / `${DB_PASSWORD}` / `${DB_NAME}` substitution. |
| `txData/Qbox_F913B4.base/server.cfg.bkp`          | Same as above (and probably worse — older snapshot)    | Don't migrate; delete after diffing for any unique config.        |
| `txData/admins.json`                              | bcrypt password hashes for `Vizuu_3D` and `vzu`        | **Stays outside repo.** Live on the dev box / prod box only.      |
| `txData/Qbox_F913B4.base/.replxx_history`         | FXServer console history — may include secrets         | Don't migrate; gitignore future copies.                           |
| `.env`                                            | All real DB / RCON / license values                    | **Stays outside repo.** Ship `.env.example` with names only.      |

A pre-commit hook (or CI grep) for `cfxk_`, `mysql://`, and bcrypt patterns
should land alongside the cutover.

## Migration checklist (when monorepo cutover happens)

1. Diff `server.cfg` vs `server.cfg.bkp`. Carry forward only intentional
   changes; use `.bkp` to recover anything we want.
2. Strip every secret listed above; rewrite to env-var substitution.
3. Move `vzu_circuit_hack` source into `resources/[vzu]/vzu_circuit_hack/` and
   make the txData copy a deploy artifact.
4. Move `vzu_circuit_hack_test_zone` to `tools/dev-bench/`. Add a guarded
   `ensure` only in dev fragment.
5. Vendor each `[ox]`, `[qbx]`, `[standalone]`, `[voice]`, `[assets]`,
   `[npwd]`, `[npwd-apps]` resource with a `VENDORED.md` (upstream + commit
   pin + license).
6. Open a follow-up issue for the four "Review" standalone resources.
7. Open a follow-up issue for the qbox job-prune decision (alpha-mode-driven).
8. Verify `grep -r 'cfxk_\|mysql://[a-z]' .` returns nothing in the staged
   tree before commit.
